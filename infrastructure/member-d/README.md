# Member D AWS infrastructure

Member D has two intentional CloudFormation ownership domains. They are not
duplicate deployments:

| Stack | Maintained source | Owned resources |
|---|---|---|
| `PacificBioArchive-Database` | `dynamodb.yaml` | `FilesTable`, `SubscriptionsTable`, `NotificationsTable`, `QueryLambdaRole` |
| `PacificBioArchive-QueryAdoption` | generated import template, then `query-adoption.yaml` | `ReservationsTable`, `QueryFunction`, `QueryIntegration`, routes and scoped permissions |

The deployment entry point for the existing account is
[`../../docs/member-d/aws-resource-adoption.md`](../../docs/member-d/aws-resource-adoption.md).
It is currently marked **DO NOT EXECUTE** until a separate AWS-write approval
is given. No AWS deployment was performed while preparing this implementation.

## Database stack

`dynamodb.yaml` retains exactly:

- `PacificBioArchiveFiles` (`file_id` partition key);
- `PacificBioArchiveSubscriptions` (`user_id`, `species`);
- `PacificBioArchiveNotifications` (`user_id`, `notification_id`);
- `PacificBioArchive-QueryLambdaRole`.

Its existing output keys remain `TableName`, `SubscriptionsTableName`,
`NotificationsTableName`, and `QueryLambdaRoleArn`; they are not exported or
temporarily changed for adoption. The role consumes ordinary parameters for the
existing reservations-table ARN, private input bucket, and storage-delete
function name.

## Query adoption stack

The initial standalone import model is generated by
`import/prepare_import.py`. It contains exactly 19 retained existing resources:

- `ReservationsTable`;
- `QueryFunction`;
- `QueryIntegration`;
- 16 Member D non-OPTIONS routes.

It has no Outputs or secret parameter. Physical identifiers are generated from
a fresh audit into `resources-to-import.json`; the operator never hand-enters
the 19 identifiers. Cross-stack bindings are ordinary, validator-checked role
ARN/API/authorizer parameters, not `Fn::GetAtt` or exports.

After a separately approved IMPORT and mandatory post-import evidence gate,
`query-adoption.yaml` is the normal-UPDATE source. The first UPDATE validator
allows exactly:

- one non-replacing `QueryFunction` modification;
- ten OPTIONS route additions;
- 26 method/path-scoped `AWS::Lambda::Permission` additions.

It forbids Remove/Replace, wildcard permissions, source-stack resources and a
`QueryLambdaRole` change. It does not add SNS resources. Durable in-app
notifications continue to use the database-owned notifications table; email
activation needs a separately approved IAM/SNS design.

`InternalApiKey` appears only in this later update template as a `NoEcho`
parameter. Its value must be entered only in the CloudFormation Console during
that separately approved phase—never in CLI arguments, environment variables,
files, logs, screenshots, Git or chat.

## Object and species-directory model

Media objects remain under stable user/file-scoped S3 keys. Species navigation
is a logical DynamoDB tag directory. No deployment path copies or moves an S3
object into per-species folders, so multi-species media does not create duplicate
objects or inconsistent deletion paths.

## Local validation

From the repository root:

```powershell
python -m pytest infrastructure/member-d/import/test_adoption.py infrastructure/member-d/import/test_prepare_import.py infrastructure/member-d/test_template.py -q -p no:cacheprovider
```

The local tests validate our artifact and Change Set contracts. They do not
authorize AWS writes or replace a real CloudFormation preview.
